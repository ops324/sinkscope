# SinkScope

[![CI](https://github.com/ops324/sinkscope/actions/workflows/ci.yml/badge.svg)](https://github.com/ops324/sinkscope/actions/workflows/ci.yml)

地盤沈下モニタリング＆下水道点検トリアージ WebGIS

**▶ デモを見る（サーバ・DB不要）: https://ops324.github.io/sinkscope/**
共有しているのは固定デモのスナップショットであり、ライブに更新されるサービスではない。

> 検出科学（陥没そのものの検知）では競わない ― そこはNTT等の研究開発の領分。
> 誰も公開データで示していない「公開衛星データ → 自治体が使えるGIS意思決定レイヤー」の
> ラストマイルを、100%実データで完結するE2Eの成果物として実証する。

## この作品で見てほしいこと（3分で読む用）

将来的な**商用PoCを見据えて個人開発している**、公開衛星データ×社会インフラの
参照実装です。**今日の位置づけは「製品」ではなく「誠実なPoC・参照実装」**であり、
その区別自体を作品の核に置いています。

- **技術力**: GeoDjango/PostGIS＋React/deck.glのフルスタックを、5系統の公的実データ
  取込（GSI衛星SAR・KSJ土地利用・地理院DEM・OSM・MLIT陥没）で動かし、空間
  パーミュテーション検定＋Moran's I診断まで実装。CIと[再現性ハーネス](#再現性reproducibility)で
  「主張」を「検証可能」にしている。
- **誠実さ（この作品の主眼）**: 目的は"当たる予測器"を騙ることではなく、
  **何を主張でき／できないかを厳密に示し、それを機械で強制・再現すること**。
  たとえば「陥没箇所は地盤沈下が強い」という中核仮説は検定で**支持されず**（片側p=0.962）、
  優先度は道路長との順位相関ρ=0.903で「ほぼ道路長の地図」に近い ── これらは
  失敗の隠蔽対象ではなく、**自分の作ったものを正直に評価し、埋めるべき差分を特定
  できることの証拠**として、コード・API・UI・本READMEに常設開示している。
- **商用への視座**: その「埋めるべき差分」を[商用化ロードマップ](#商用化ロードマップ)に
  具体化している。これは"いつか商用にしたい"という願望ではなく、正直な現状（ρ=0.903）から
  実価値までの道筋を、難度と次の一手つきで書いたもの。

> **なぜ作ったか**：八潮の陥没事故が示した通り、老朽インフラの点検は「限られた予算で、
> どこから見るか」の問題だ。公開衛星データはその判断を助けられるのに、自治体が使える形に
> なっていない ── その"ラストマイル"を、過大主張せず誠実に埋められることを示す参照実装を
> 目指した。

## これは何か

老朽化した下水道管に起因する道路陥没（2025年1月・埼玉県八潮市の事故など）を受け、
国土交通省は全国の自治体に老朽下水道管の緊急点検を要請している。一方で点検予算・人員は
限られており、どこから手をつけるかの優先順位づけが課題になっている。

SinkScopeは、**国土地理院が無償公開している衛星SAR（InSAR）地盤変動測量成果**を主軸に、
「地盤沈下がどこでどう進行しているか」を面的に可視化し、それを自治体の点検優先度判断に
使えるトリアージ情報へ翻訳するWebGISである。

**このシステムが「できないこと」を最初に明記する**：InSARの実効分解能（数十〜100m）は、
マンホール（直径0.6m程度）や個々の下水管の状態を個別に見分けるには粗すぎる。また、
下水管の損傷による突発的・局所的な陥没（八潮市の事故はこの典型例）は、そもそもInSARが
最も苦手とする現象である。本システムが提供するのは、そうした個別予測ではなく、
**面的な脆弱域の点検優先度づけ**である。

## 構成：Monitor → Triage

SinkScopeは1つのプロダクトの中に、信頼度の異なる2つのモジュールを明確に分けて持つ。

### Monitor（100%実データ）
- 国土地理院「衛星SAR地盤変動測量成果」による地盤変位・地盤/地形/道路の面的統合（250mメッシュ）
- 国土交通省が公表する道路陥没オープンデータの実イベントを、予測ターゲットではなく
  グラウンドトゥルースの重ね合わせとして地図上に提示（視覚的な答え合わせ）
- AOI内の実イベント数を正直に開示した上で、n(下水道原因)が十分な場合に限り、
  空間パーミュテーション検定という単一の反証可能な検定を付録として実施

Monitorには合成データを一切含めない。ここがこのプロダクトの信頼の核。

**「沈下の加速度検出」「陥没危険度の予測」は行わない**：当初計画していた沈下加速度検出は、
GSIから得られるのが年度スナップショット1枚のみという制約により実装不能と判明した。また
陥没危険度の回帰・スコアリングは、地質データ未投入・InSAR精度限界・イベントの字重心への
集約といった制約下では誠実に成立しないと、2度の独立した設計レビューで判断した。詳細と
判断の経緯は [docs/SPEC.md](./docs/SPEC.md) §7を参照。

### Triage（意思決定支援層）
- Monitorの実成果を、メッシュ単位の点検優先度ランキング（高／中／低のtier）に翻訳
- 疑似管路データ（実際の管路台帳の代わりに道路網上へ合成配置）は **Illustrative** バッジで
  明示し、実データの成果と混同させない
- 点検優先度は「資産単位の故障予測」ではなく「面的な脆弱域のトリアージ」であることを常設パネルで明示

**「Illustrative」はデータだけでなく手法にもかかる**：疑似管路が架空データであることに加え、
優先度算出のヒューリスティック自体が未検証であることを常設パネル・APIレスポンス双方で
明示する（Monitorの検定が仮説を支持しなかったため。上記参照）。連続的な「優先度スコア」は
一切公開せず、tier（高/中/低）のみを示す。

**誠実な自己点検（本PRの実測結果）**：優先度と「道路長だけの単純なランキング」との
Spearman順位相関は **ρ=0.903**（本AOI・デフォルト重み）。これは高く、本ランキングが
docs/SPEC.md §7.1で警戒した「実質、道路長の地図をハザード色で偽装するだけ」というリスクに
現状かなり近いことを意味する。この値は隠さずTriageパネルに常設表示し、利用者自身が
判断材料にできるようにしている。詳細設計は [docs/SPEC.md](./docs/SPEC.md) §9を参照。

## 実データ・合成データ・原理的にできないこと

| 区分 | 内容 |
|---|---|
| 実データ | 国土地理院 衛星SAR地盤変動測量成果、国土数値情報（土地利用）、DEM、OSM道路網、国交省道路陥没オープンデータ |
| 合成データ（Illustrative） | 疑似管路の幾何（OSM道路センターライン上へ配置）・布設年・管種。優先度算出の手法（重み付きヒューリスティック）自体も未検証 |
| 未実装（将来の拡張用フィールドのみ存在） | 地質・地盤分類（`GroundClass.geology_class`/`ground_classification`）、気象庁解析雨量（無償・自動・historicalを同時に満たす公式ルートが無く、当初計画から対象外化。詳細は[docs/SPEC.md](./docs/SPEC.md) §6）。下水道統計は取込対象としていない |
| 原理的にできないこと | マンホール／単一管路単位での沈下分離、突発・局所的な陥没の予兆検知 |

## デモを動かす（最短・外部ネット不要）

`docker compose up` 直後のDBは空で、地図に実データを出すには本来
`ingest_all`→`build_monitor`→`generate_triage` を手動実行する必要があり、各取込は
政府の生きたエンドポイントへ実HTTP取得する（遅く・不安定・ネット必須）。読み手が
これを踏むのは非現実的なので、**コミット済みのデータスナップショット
（`backend/analysis/fixtures/golden_snapshot.json.gz`）からオフラインで投入する**
ワンコマンドを用意した：

```bash
make demo
# → build → PostGIS起動 → migrate → snapshot投入 → バックエンド起動（外部取得なし）

# フロントエンド（別ターミナル）
cd frontend && npm install && npm run dev   # → http://localhost:5173
```

表示される数値（片側p=0.9616・Moran's I=0.797・道路長との順位相関 ρ=0.903）は、
[再現ハーネス](#再現性reproducibility)がCIで継続検証している値と同一である
（"見栄え用の別データ"を作っていない）。`make help` でタスク一覧。

## シェア用の静的サイト（リンク1つで共有・サーバ/DB不要）

デモデータは golden snapshot で固定なので、API応答をあらかじめJSONへ焼き固めれば、
**サーバもデータベースも不要の完全静的サイト**として配布できる。生成物 `frontend/dist/` は
そのまま任意の静的ホスティングに置ける。

```bash
make static
# → seed_demo(golden snapshot) → export_static でAPI応答をJSON化 → 静的ビルド(build:static)
# 出力: frontend/dist（ローカル確認は  npx serve frontend/dist ）
```

焼き固めJSON（`frontend/public/data/*.json`）は本物のAPI view関数（`backend/api/views.py`）から
`export_static` コマンドで生成したもので、ライブAPIとバイト等価（"見栄え用の別データ"を作らない）。
実行ごとに揺れるのは生成時刻とpkのみで、実データ（変位速度・イベント・tier・ρ=0.903 等の
metrics・disclaimers）が一致することはCIの `static-export` ジョブが継続検証する
（`export_static --check`、時刻/pkは意味的比較で除外）。

**GitHub Pages で自動公開（稼働中）**：`.github/workflows/pages.yml` が main への push で
`frontend/dist` を Pages へデプロイする。公開URL: https://ops324.github.io/sinkscope/
（サブパスは `frontend/vite.config.ts` の `STATIC_BASE` と対応。リポジトリ名が違う場合は
ここを変更する。フォークして自分の Pages で動かす場合は、初回のみ Settings → Pages →
Source を「GitHub Actions」に設定すること）。

> 共有するのは **固定デモのスナップショット** であり、ライブに更新されるサービスではない。
> 地図タイル・地名検索は国土地理院の公開API（CORS許可済み）を直接呼ぶため、静的サイトでも動く。

焼き固めJSONは合計約26MB（疑似管路が大半）と大きいため **Git LFS** で管理している
（`.gitattributes`）。クローンやビルド前に `git lfs install` が必要（未導入だと実体でなく
ポインタが取得される）。CI・Pagesの checkout は `lfs: true` で実体を取得する。

## ローカル開発環境（フル取込・実データを自分で取得する場合）

```bash
cp .env.example .env

# バックエンド + PostGIS
docker compose up --build

# 実データの取込→解析（コンテナ内、外部エンドポイントへ実取得）
docker compose exec backend python manage.py migrate
docker compose exec backend python manage.py ingest_all
docker compose exec backend python manage.py build_monitor --seed 42
docker compose exec backend python manage.py generate_triage --seed 42

# フロントエンド（別ターミナル）
cd frontend
npm install
npm run dev
```

- API ヘルスチェック: `http://localhost:8000/api/health/`
- フロントエンド: `http://localhost:5173`

## 再現性（Reproducibility）

[docs/ASSESSMENT.md](./docs/ASSESSMENT.md) に記載した実測値（片側p値=0.9616,
Moran's I=0.797, 道路長とのSpearman順位相関ρ=0.903）は、文書化するだけでなく、
誰でも自分の手で再現・検証できる。

```bash
./scripts/reproduce.sh
```

開発中の`docker compose up`環境には一切触れない使い捨て環境で、コミット済みの
入力データ（`backend/analysis/fixtures/golden_snapshot.json.gz`）から
`build_monitor`→`generate_triage`を再実行し、得られた値が
[docs/SNAPSHOT.md](./docs/SNAPSHOT.md) に記録した期待値と一致するかを機械的に
照合する。入力データの来歴・既知の欠落・検証済みの実行記録は
[docs/SNAPSHOT.md](./docs/SNAPSHOT.md) を参照。

## Future Work（本プロジェクトのスコープ外とした理由）

- **自前InSAR時系列処理（Sentinel-1 / ASF HyP3・LiCSBAS）**: 国土地理院の公開成果で
  実データによる可視化・検証は十分に成立するため、自前処理は本プロジェクトの中核的な
  価値提案（GISラストマイルの実証）には必須でないと判断し対象外とした。

  **この判断は後日、別リポジトリ [s1-insar-minimal](https://github.com/ops324/s1-insar-minimal)
  で実際に検証した。** Sentinel-1 IW SLC の
  単一サブスワス・単一バーストペア（同一軌道 path 46 降交・同一バースト・3ペア）を
  ESA SNAP で自前処理し、次の実測値を得た。

  | 測った量 | 実測値 |
  |---|---|
  | 密集市街地の12日ペアのコヒーレンス（中央値） | γ̂ = 0.81（位相は十分読める） |
  | 残差位相（γ̂≥0.7 の画素、1 km ブロック内） | 0.41 mm（視線方向） |
  | 残差位相（シーン全体・下限値） | ≥ 1.99 mm（視線方向） |
  | 沈下 10 mm/年 の12日ペア信号 | 0.254 mm（視線方向） |

  **目標信号は最良ペアの短波長残差の 0.62 倍**で、大気の長波長成分を持ち出すまでもなく
  1 km スケールのばらつきに埋もれる。mm/年級の沈下速度を出すには複数年の時系列解析が要り、
  単一ペアでは原理的に届かない（12日回帰で3年積んで ±0.6〜1.2 mm/年）。
  本プロジェクトが検証済みの公開成果を採ったのは、この感度差を前提とした判断だった。
  なおこれは公開成果（Lバンド）の検証ではない ── センサーも波長も期間も異なるため、
  Cバンド単一ペアでLバンド時系列成果を検証することは原理的にできない。
- **ALOS-4/PALSAR-3の自前SLC処理**: 2026年時点でPALSAR-3のオープンソース処理系
  （SNAP対応は2025年9月〜、ISCE2等の対応は未確認）は成熟しておらず、費用対効果が
  見合わないため対象外とした。
- **ライブサービスのクラウドデプロイ**: 認証・自動データ更新・SLAを伴う本番運用は
  引き続きスコープ外（[商用化ロードマップ](#商用化ロードマップ)参照）。ただし
  **固定デモの共有可能な静的サイト** は `make static` / GitHub Pages で提供する
  （上記[シェア用の静的サイト](#シェア用の静的サイトリンク1つで共有サーバdb不要)）。

## 商用化ロードマップ

本プロジェクトは誠実なPoC（実証）であり、商用プロダクトそのものではない。
**将来的な商用PoCを見据えて**、何があれば商用グレードに接続できるかを、差分を
隠さずここに明記する。「次の一手」は、限られた工数で最初に着手すべき、検証可能な
一歩を優先度順に示したもの。

| 項目 | 現状 | 商用化に必要なもの | 次の一手（最初の検証可能な一歩） | 想定難度 |
|---|---|---|---|---|
| 管路データ | 合成管路（Illustrative、道路網上へ配置） | 自治体の実管路台帳（布設年・管種・口径・埋設深） | 1自治体分の管路GISを協働で入手し、合成管路を実台帳に差し替えてTriageがそのまま動くことを示す（スキーマは既に実管路を受けられる形） | 高（データ提供元との調整が前提） |
| 予測価値の実証 | 道路密度ベースラインを統計的に上回る根拠は未取得。優先度も道路長単独ランキングとの順位相関ρ=0.903と高く、独立した予測価値は未実証 | AOI拡大や年度蓄積によるイベントn確保＋実管路特徴量での再検証 | **道路長と独立な実susceptibility特徴量（地盤/微地形分類）を1つ追加し、事前登録した重みでρが下がるかを再測定**。上下どちらの結果も[再現性ハーネス](#再現性reproducibility)で公開する（"独立性"は改善しうるが"妥当性"(p=0.962)は別問題、と明示） | 高 |
| 運用化 | ローカルでの一括ingest・単発解析 | 自治体単位の設定・自動データ更新パイプライン・監視・QA | AOIを設定ファイル化し、GSI成果の年度更新を検知して再ingestする仕組みを1本用意 | 中 |
| 基盤 | ローカルDocker Compose | クラウドデプロイ・認証・アクセス制御・SLA | 現行Composeをそのままマネージド環境（1コンテナ＋マネージドPostGIS）へ載せ、認証を前段に置く | 中 |
| 現場・制度適合 | 未実施 | 土木専門家による妥当性確認、MLIT下水道ストックマネジメント枠組み・調達要件との整合、監査可能性の担保 | 土木専門家1名にTriage出力をレビューしてもらい、"現場が実際に見る指標"とのギャップを洗い出す | 高 |

> 「次の一手」で最も価値が高いのは**予測価値の実証**の行。独立特徴量の追加は、
> 受け皿（`GroundClass.geology_class` / `ground_classification`）が既に用意済みで、
> **データ入手性は実測で確認済み**：J-SHIS（防災科研）の表層地盤データ **V4（2020年版）**
> が `Z-V4-JAPAN-AMP-VS400_M250-{1次メッシュコード}.zip` として認証不要で取得できる
> （本AOIは東京＝`5339` の1ファイル・約851KB・CSV列は `CODE, JCODE, AVS, ARV`。
> `JCODE`＝微地形区分24分類、`AVS`＝表層30mの平均S波速度）。
>
> ただし**全国一括ファイルは存在せず**、配布単位は1次メッシュである。また
> **メッシュコードによる結合はできない**：本プロジェクトの250mメッシュは平面直角座標系
> IX系（EPSG:6677）上の等面積グリッド（`backend/core/mesh.py`）であるのに対し、J-SHIS は
> 緯度経度ベースのJIS地域メッシュで、**解像度は同じ250mでも格子の切り方が異なる**
> （実測：本AOIの7,918メッシュとJ-SHIS側コードの一致は0件）。したがって取込は
> 空間結合になり、既存の土地利用取込（`backend/ingest/kokudo_suuchi.py`）と同じく
> メッシュ重心での代表値抽出という設計判断が必要になる（境界セルでは最大1セル分ずれうる）。
>
> **この「次の一手」は一度着手し、設計を事前登録したうえで独立監査にかけ、測定を実施せずに
> 撤回した。**経緯は [docs/PREREGISTRATION.md](./docs/PREREGISTRATION.md) に記録してある。
>
> 撤回の理由は、**この検証設計に情報量がなかった**こと。道路長と無相関な項を重み0.2で足せば
> 中身が何であれ ρ は下がり、実測では susceptibility を**純粋な乱数にした方が「良い」ρ
> （0.531）**を出した（AVS30 は 0.852）。空間結合のバグまでが望ましい結果として報われる。
> 加えて AVS30 は微地形区分から推定されたモデル値であり「連続実測値だから恣意性がない」
> という登録時の前提が誤りだったこと、陥没の律速要因は剛性ではなく土砂の侵食性であり
> `-AVS30` が最重要リスク単元（旧河道の砂）を泥炭より下位に並べることも判明した。
>
> よって次に測るには、**陰性対照アーム（空間シャッフル・乱数場）と ρ 算出式の凍結、
> 判定閾値と撤回規則**が最低限必要になる。指標も機序（侵食性・地下水位・埋設深）から
> 選び直す必要がある。詳細は上記文書 §5.1 に要件として残した。
> 利用規約上、加工した派生値（メッシュ単位の分類）の頒布は可・生データそのままの
> 再頒布は不可（J-SHIS利用規約 第5条）。転載・引用時は同規約 第4条により
> 若松・松岡(2013) / Wakamatsu and Matsuoka (2013)、AVS30を用いる場合は
> 松岡・若松(2008) の引用が必要である点も、実装時に明記する。
