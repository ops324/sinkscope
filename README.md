# SinkScope

地盤沈下モニタリング＆下水道点検トリアージ WebGIS

> 検出科学（陥没そのものの検知）では競わない ― そこはNTT等の研究開発の領分。
> 誰も公開データで示していない「公開衛星データ → 自治体が使えるGIS意思決定レイヤー」の
> ラストマイルを、100%実データで完結するE2Eの成果物として実証する。

## これは何か

老朽化した下水道管に起因する道路陥没（2025年1月・埼玉県八潮市の事故など）を受け、
国土交通省は全国の自治体に老朽下水道管の緊急点検を要請している。一方で点検予算・人員は
限られており、どこから手をつけるかの優先順位づけが課題になっている。

SinkScopeは、**国土地理院が無償公開している衛星SAR（InSAR）地盤変動測量成果**を主軸に、
「地盤沈下がどこでどう進行しているか」を面的に可視化し、それを自治体の点検優先度判断に
使えるトリアージ情報へ翻訳するWebGISである。

**このシステムが「できないこと」を最初に明記する**：InSARの実効分解能（数十〜100m）は、
マンホール（直径0.6m程度）や個々の下水管の状態を個別に見分けるには粗すぎる。また、
下水管の損傷による突発的・局所的な陥没（八潮市の事故はこの典型例）は、そもそもInSARが
最も苦手とする現象である。本システムが提供するのは、そうした個別予測ではなく、
**面的な脆弱域の点検優先度づけ**である。

## 構成：Monitor → Triage

SinkScopeは1つのプロダクトの中に、信頼度の異なる2つのモジュールを明確に分けて持つ。

### Monitor（100%実データ）
- 国土地理院「衛星SAR地盤変動測量成果」による地盤変位・地盤/地形/道路の面的統合（250mメッシュ）
- 国土交通省が公表する道路陥没オープンデータの実イベントを、予測ターゲットではなく
  グラウンドトゥルースの重ね合わせとして地図上に提示（視覚的な答え合わせ）
- AOI内の実イベント数を正直に開示した上で、n(下水道原因)が十分な場合に限り、
  空間パーミュテーション検定という単一の反証可能な検定を付録として実施

Monitorには合成データを一切含めない。ここがこのプロダクトの信頼の核。

**「沈下の加速度検出」「陥没危険度の予測」は行わない**：当初計画していた沈下加速度検出は、
GSIから得られるのが年度スナップショット1枚のみという制約により実装不能と判明した。また
陥没危険度の回帰・スコアリングは、地質データ未投入・InSAR精度限界・イベントの字重心への
集約といった制約下では誠実に成立しないと、2度の独立した設計レビューで判断した。詳細と
判断の経緯は [docs/SPEC.md](./docs/SPEC.md) §7を参照。

### Triage（意思決定支援層）
- Monitorの実成果を、メッシュ単位の点検優先度ランキング（高／中／低のtier）に翻訳
- 疑似管路データ（実際の管路台帳の代わりに道路網上へ合成配置）は **Illustrative** バッジで
  明示し、実データの成果と混同させない
- 点検優先度は「資産単位の故障予測」ではなく「面的な脆弱域のトリアージ」であることを常設パネルで明示

**「Illustrative」はデータだけでなく手法にもかかる**：疑似管路が架空データであることに加え、
優先度算出のヒューリスティック自体が未検証であることを常設パネル・APIレスポンス双方で
明示する（Monitorの検定が仮説を支持しなかったため。上記参照）。連続的な「優先度スコア」は
一切公開せず、tier（高/中/低）のみを示す。

**誠実な自己点検（本PRの実測結果）**：優先度と「道路長だけの単純なランキング」との
Spearman順位相関は **ρ=0.903**（本AOI・デフォルト重み）。これは高く、本ランキングが
docs/SPEC.md §7.1で警戒した「実質、道路長の地図をハザード色で偽装するだけ」というリスクに
現状かなり近いことを意味する。この値は隠さずTriageパネルに常設表示し、利用者自身が
判断材料にできるようにしている。詳細設計は [docs/SPEC.md](./docs/SPEC.md) §9を参照。

## 実データ・合成データ・原理的にできないこと

| 区分 | 内容 |
|---|---|
| 実データ | 国土地理院 衛星SAR地盤変動測量成果、国土数値情報（地質・地盤分類・土地利用）、気象庁解析雨量、DEM、OSM道路網、国交省道路陥没オープンデータ、下水道統計 |
| 合成データ（Illustrative） | 疑似管路の幾何（OSM道路センターライン上へ配置）・布設年・管種。優先度算出の手法（重み付きヒューリスティック）自体も未検証 |
| 原理的にできないこと | マンホール／単一管路単位での沈下分離、突発・局所的な陥没の予兆検知 |

## 技術スタック

- バックエンド: Django + GeoDjango + PostGIS
- フロントエンド: React + TypeScript + Vite、Mapbox GL / MapLibre、deck.gl
- 解析: Python（GeoPandas, rasterio, scikit-learn, XGBoost, SHAP）
- インフラ: Docker Compose（ローカル開発）

## ローカル開発環境

```bash
cp .env.example .env

# バックエンド + PostGIS
docker compose up --build

# フロントエンド（別ターミナル）
cd frontend
npm install
npm run dev
```

- API ヘルスチェック: `http://localhost:8000/api/health/`
- フロントエンド: `http://localhost:5173`

## Future Work（本プロジェクトのスコープ外とした理由）

- **自前InSAR時系列処理（Sentinel-1 / ASF HyP3・LiCSBAS）**: 国土地理院の公開成果で
  実データによる可視化・検証は十分に成立するため、自前処理は本プロジェクトの中核的な
  価値提案（GISラストマイルの実証）には必須でないと判断し対象外とした。
- **ALOS-4/PALSAR-3の自前SLC処理**: 2026年時点でPALSAR-3のオープンソース処理系
  （SNAP対応は2025年9月〜、ISCE2等の対応は未確認）は成熟しておらず、費用対効果が
  見合わないため対象外とした。
- **クラウドデプロイ**: ローカルDocker Composeでの再現性を優先し、デプロイは
  スコープ外とした。

## 商用化ロードマップ

本プロジェクトは誠実なPoC（実証）であり、商用プロダクトそのものではない。何があれば
商用グレードに接続できるかを、差分を隠さずここに明記する。

| 項目 | 現状 | 商用化に必要なもの | 想定難度 |
|---|---|---|---|
| 管路データ | 合成管路（Illustrative、道路網上へ配置） | 自治体の実管路台帳（布設年・管種・口径・埋設深） | 高（データ提供元との調整が前提） |
| 予測価値の実証 | 道路密度ベースラインを統計的に上回る根拠は未取得。Triageの優先度も道路長単独ランキングとの順位相関ρ=0.903と高く、独立した予測価値は未実証（本PRの誠実な結論） | AOI拡大や年度蓄積によるイベントn確保＋実管路特徴量での再検証 | 高 |
| 運用化 | ローカルでの一括ingest・単発解析 | 自治体単位の設定・自動データ更新パイプライン・監視・QA | 中 |
| 基盤 | ローカルDocker Compose | クラウドデプロイ・認証・アクセス制御・SLA | 中 |
| 現場・制度適合 | 未実施 | 土木専門家による妥当性確認、MLIT下水道ストックマネジメント枠組み・調達要件との整合、監査可能性の担保 | 高 |
