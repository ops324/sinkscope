# SinkScope

地盤沈下モニタリング＆下水道点検トリアージ WebGIS

> 検出科学（陥没そのものの検知）では競わない ― そこはNTT等の研究開発の領分。
> 誰も公開データで示していない「公開衛星データ → 自治体が使えるGIS意思決定レイヤー」の
> ラストマイルを、100%実データで完結するE2Eの成果物として実証する。

## これは何か

老朽化した下水道管に起因する道路陥没（2025年1月・埼玉県八潮市の事故など）を受け、
国土交通省は全国の自治体に老朽下水道管の緊急点検を要請している。一方で点検予算・人員は
限られており、どこから手をつけるかの優先順位づけが課題になっている。

SinkScopeは、**国土地理院が無償公開している衛星SAR（InSAR）地盤変動測量成果**を主軸に、
「地盤沈下がどこでどう進行しているか」を面的に可視化し、それを自治体の点検優先度判断に
使えるトリアージ情報へ翻訳するWebGISである。

**このシステムが「できないこと」を最初に明記する**：InSARの実効分解能（数十〜100m）は、
マンホール（直径0.6m程度）や個々の下水管の状態を個別に見分けるには粗すぎる。また、
下水管の損傷による突発的・局所的な陥没（八潮市の事故はこの典型例）は、そもそもInSARが
最も苦手とする現象である。本システムが提供するのは、そうした個別予測ではなく、
**面的な脆弱域の点検優先度づけ**である。

## 構成：Monitor → Triage

SinkScopeは1つのプロダクトの中に、信頼度の異なる2つのモジュールを明確に分けて持つ。

### Monitor（100%実データ）
- 国土地理院「衛星SAR地盤変動測量成果」による地盤変位・沈下速度
- 沈下の加速度・トレンド変化検出（「どこで沈下が加速しているか」）
- 国土交通省が公表する道路陥没オープンデータとの空間相関検証（反証可能な検証フック）
- 陥没報告密度の回帰分析（InSAR変位・地質・標高等を特徴量とし、報告バイアスを曝露オフセットで補正）

Monitorには合成データを一切含めない。ここがこのプロダクトの信頼の核。

### Triage（意思決定支援層）
- Monitorの実成果を、メッシュ／排水区単位の点検優先度ランキングに翻訳
- 疑似管路データ（実際の管路台帳の代わりに道路網上へ合成配置）は **Illustrative** バッジで
  明示し、実データの成果と混同させない
- 点検優先度は「資産単位の故障予測」ではなく「面的な脆弱域のトリアージ」であることを常設パネルで明示

## 実データ・合成データ・原理的にできないこと

| 区分 | 内容 |
|---|---|
| 実データ | 国土地理院 衛星SAR地盤変動測量成果、国土数値情報（地質・地盤分類・土地利用）、気象庁解析雨量、DEM、OSM道路網、国交省道路陥没オープンデータ、下水道統計 |
| 合成データ（Illustrative） | 疑似管路の布設年・管種、街区スケールの内挿 |
| 原理的にできないこと | マンホール／単一管路単位での沈下分離、突発・局所的な陥没の予兆検知 |

## 技術スタック

- バックエンド: Django + GeoDjango + PostGIS
- フロントエンド: React + TypeScript + Vite、Mapbox GL / MapLibre、deck.gl
- 解析: Python（GeoPandas, rasterio, scikit-learn, XGBoost, SHAP）
- インフラ: Docker Compose（ローカル開発）

## ローカル開発環境

```bash
cp .env.example .env

# バックエンド + PostGIS
docker compose up --build

# フロントエンド（別ターミナル）
cd frontend
npm install
npm run dev
```

- API ヘルスチェック: `http://localhost:8000/api/health/`
- フロントエンド: `http://localhost:5173`

## Future Work（本プロジェクトのスコープ外とした理由）

- **自前InSAR時系列処理（Sentinel-1 / ASF HyP3・LiCSBAS）**: 国土地理院の公開成果で
  実データによる可視化・検証は十分に成立するため、自前処理は本プロジェクトの中核的な
  価値提案（GISラストマイルの実証）には必須でないと判断し対象外とした。
- **ALOS-4/PALSAR-3の自前SLC処理**: 2026年時点でPALSAR-3のオープンソース処理系
  （SNAP対応は2025年9月〜、ISCE2等の対応は未確認）は成熟しておらず、費用対効果が
  見合わないため対象外とした。
- **クラウドデプロイ**: ローカルDocker Composeでの再現性を優先し、デプロイは
  スコープ外とした。
