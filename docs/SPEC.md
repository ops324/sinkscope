# SinkScope 技術仕様書

README が「何を・なぜ作るか」のピッチだとすれば、本書は「実際に何を、どう検証して
作ったか」の技術詳細である。特に第4章（データソースの実アクセス方法）は、公開情報だけ
からは分からず実機検証して初めて分かった内容を記録している。

---

## 1. スコープと構成

SinkScope は1プロダクト・2モジュール構成を取る。

- **Monitor**：100%実データ。国土地理院の衛星SAR変位速度を核に、地盤・地形・道路・
  過去の陥没事案という実データを同一の空間グリッドに統合する。
- **Triage**：Monitor の実成果を点検優先度に翻訳する意思決定支援層。疑似管路データを
  ここに限定し、`Illustrative` バッジで実データと区別する（設計方針は README 参照）。

本書は主に Monitor のデータ基盤（実装済み）を扱う。Triage の詳細設計は該当PRで追記する。

---

## 2. データモデル

すべて `backend/core/models.py` に定義。共通の空間単位は `MeshCell`（250mメッシュ）で、
他の全テーブルはこれに `ForeignKey`/`OneToOneField` で紐づく。

| モデル | 主なフィールド | 内容 | 実データ元 |
|---|---|---|---|
| `MeshCell` | `mesh_code`, `geom`, `centroid` | 全レイヤー共通の250m格子 | ― |
| `DisplacementVelocity` | `mesh_cell`, `fiscal_year`, `velocity_cm_per_year` | 準上下方向の変位速度（cm/年） | 国土地理院 衛星SAR地盤変動測量成果 |
| `GroundClass` | `mesh_cell`, `land_use_class`, `elevation_m`, `geology_class`*, `ground_classification`* | 土地利用・標高（geology/ground_classificationは未実装、下記参照） | KSJ土地利用細分メッシュ、地理院標高タイル |
| `RoadExposure` | `mesh_cell`, `road_length_m` | メッシュ内道路延長（曝露オフセット用） | OpenStreetMap |
| `SubsidenceEvent` | `mesh_cell`, `fiscal_year`, `location_text`, `cause_facility`, `geocode_confidence` | 道路陥没事案（ジオコーディング済み） | 国土交通省 道路陥没オープンデータ |
| `PrecipitationObservation` | (未使用) | 降水量 | 実装見送り（第6章） |

**`DisplacementVelocity` がなぜ「日付ごとの累積変位」ではなく「年度ごとの速度」なのか**：
当初は稠密な時系列（複数時点の累積変位）を格納する設計だったが、実際に国土地理院のAPIを
呼んで確認した結果、一括ダウンロードで得られるのは年度時点での「変位速度」（観測期間全体の
線形トレンド、cm/年）1枚であり、多時点の時系列ではないと判明した。モデルはこの実態に
合わせて設計し直してある（`fiscal_year` を主キーの一部にすることで、将来別年度の成果を
同じテーブルに追加し年度間比較ができるようにしている）。詳細は第7章。

`GroundClass.geology_class` / `ground_classification` は将来の拡張用フィールドとして
モデルには残っているが、対応する取込スクリプトは未実装（KSJの「地質」データセットは
土地利用細分メッシュとは別データセットで、防災科学技術研究所のJ-SHIS(AVS30)等の代替も
検討したが今回は見送った）。

## 3. 空間設計

- **保存用座標系**：JGD2011 地理座標系（EPSG:6668）。全テーブルの `geom`/`centroid` はここに統一。
- **面積・距離計算用の投影座標系**：JGD2011 / 平面直角座標系 IX系（EPSG:6677、関東域）。
  `core/mesh.py` の `PROJECTED_SRID`。対象エリアが関東地方以外に広がる場合はここを見直す。
- **メッシュ**：250m四方の等面積グリッド。JIS X0410 の標準地域メッシュ（4分の1地域メッシュ）
  ではなく、独自の投影座標ベースグリッドを採用した。理由：等面積性が保証され、境界の
  丸め誤差がJIS標準メッシュの多段階換算より単純だったため。`mesh_code` は `"250m-{ix}-{iy}"`
  という格子インデックスで、公的な地域メッシュコードとは対応しない。
- **対象エリア**：`core/aoi.py` の `DEMO_AOI_BBOX`。江東区・江戸川区（東京都）・八潮市
  （埼玉県）周辺、(west, south, east, north) = (139.75, 35.62, 139.95, 35.86)。
  対象範囲で250mメッシュを生成すると7,918セルになる（実行・確認済み）。

## 4. データソースと検証済みアクセス方法

5つのデータソースすべて、実際にAPI/ダウンロードを叩いて中身を確認した。公開ドキュメント
だけでは分からなかった実装上の要点を記録する。

### 4.1 国土地理院 衛星SAR地盤変動測量成果（`ingest/gsi_displacement.py`）

`sarprod.gsi.go.jp` の地図UIで「データ範囲選択」→「経度緯度指定」→「データダウンロード」
と操作した際に実際に発行されるHTTPリクエストをブラウザのfetch/XHRをフックして捕捉した
結果、**ブラウザセッションに一切依存しない2段階のJSON APIであることを確認した**：

```
POST https://sarprod.gsi.go.jp/execCommand/
  {"type": ["3"], "coordinates": [west, east, south, north]}
  → {"file_name": "...", "file_size_MB": ..., "zip_path": "...", "cmd_types": ["3"]}

POST https://sarprod.gsi.go.jp/downloadfile/
  {"file_info": <execCommandのレスポンスそのまま>}
  → zip バイナリ（中に GeoTIFF 1枚）
```

`type: "3"` が「準上下方向」変位速度（南行=1、北行=2、準東西=4 とレイヤー定義ファイル
`layers_for_sar.txt` から対応付け）。Cookie無しの `requests` セッションで完全に再現できる
ことを確認済み（`docker compose exec backend python -c "..."` で実データを取得しテスト）。

取得したGeoTIFFは EPSG:6668、float32、空間分解能約90m。対象エリアの実測値は
**-1.80〜+0.10 cm/年、平均-0.072 cm/年**（沈降側に偏る）で、江東区・江戸川区が
地盤沈下による「ゼロメートル地帯」として知られていることと整合する。

**重要な制約**：このAPIで得られるのは常に「現在の年度成果」1枚の変位速度スナップショット
であり、稠密な多時点の時系列ではない。マップUIの「時系列グラフ閲覧」機能は点単位の閲覧を
想定しており、エリア一括の時系列ダウンロードに対応するAPIは（レイヤー設定ファイルを見る
限り）現時点で見当たらない。「2023年度成果」フォルダも別手法（緊急解析）のプロダクトで、
単純な年度間比較には使えない。この制約が第7章の未決定事項に直結する。

### 4.2 国土数値情報（KSJ）土地利用細分メッシュ（`ingest/kokudo_suuchi.py`）

- 配布は**1次メッシュ（約80km四方）単位**。ファイル名は
  `L03-b-{年度2桁}_{1次メッシュ4桁}-{測地系}_GML.zip`。対象エリアは1次メッシュ
  **`5339`** 1枚に収まる（実際にdatalistページのHTMLを取得し `DownLd()` 呼び出しの
  パスパターンから確認）。
- zipには Shapefile（属性はShift-JIS）と GeoJSON（UTF-8、`crs`フィールドに
  `EPSG::6668` と明記）が同梱。**文字コード問題を避けるためGeoJSONを読む**。
- 1次メッシュ内には100m細分メッシュのポリゴンが約63万件含まれる。素朴に全件を
  DBへ格納せず、投影座標系で重心を計算してからMeshCellへ空間結合し、メッシュごとの
  最頻値（mode）を代表の土地利用種別として保存する。

### 4.3 標高（`ingest/dem.py`）

基盤地図情報の生GML DEM（`fgd.gsi.go.jp`）は現在DNSが解決せず、後継の
`service.gsi.go.jp/kiban` は利用者登録（氏名・住所等の入力）が必要。代わりに
**認証不要の地理院タイル（標高タイル、PNG形式）** を使う。

RGB→標高値の変換式は `https://maps.gsi.go.jp/development/demtile.html` に記載が
あるが、**単純にHTMLをテキスト化すると指数表記（`<sup>`タグ）が失われ、数式の桁が
文字化けする**（`2^23` が `223` に見えるなど）。生HTMLを直接確認して以下の正しい式を
検証済み：

```
x = 2^16 R + 2^8 G + B
x <  2^23  →  h = x * u       (u = 0.01m)
x == 2^23  →  h = NA          ((R,G,B)=(128,0,0) がこれに一致)
x >  2^23  →  h = (x - 2^24) * u
```

DEM5A（航空レーザ、最高精度）→DEM5B→DEM10B（全国網羅）の順にフォールバックする
（タイル単位で404なら次を試す）。ズームレベルは5m解像度に対応する15を使用。
対象エリアの標高実測値は **-6.36m〜30.13m、平均4.77m** で、江東区・江戸川区の
既知の海抜ゼロ以下エリアと整合する。

### 4.4 OpenStreetMap 道路網（`ingest/osm_roads.py`）

Overpass API（`overpass-api.de`）。**汎用的なUser-Agentだと`406 Not Acceptable`で
拒否される**ため、識別可能なUser-Agentを付与する必要がある（Overpass APIの利用
ガイドラインにも明記）。道路（`highway`タグ）を取得し、メッシュごとの重なり長を
線分とメッシュポリゴンの厳密な交差計算（`intersection().length`）で求める（中心点
判定などの近似は使っていない）。対象エリアで7,082メッシュに道路延長を付与、
平均約1,322m/メッシュ、最大約4,494m/メッシュ（都市部の道路密度として妥当）。

### 4.5 国土交通省 道路陥没オープンデータ（`ingest/kanbotsu_xlsx.py`）

令和5・6年度分がXLSXで直接ダウンロード可能（認証不要）。**シート構成・列位置が
年度によって微妙に異なる**ことを実際にファイルを開いて確認した（例：R6の
「都道府県」シートには R5に無い「管理者区分」列が追加されており、この列は
中身が `#REF!`（Excelの参照エラー）で実質使用不可）。このため列位置を固定せず、
ヘッダー行のラベル文字列から動的に検出する実装にしてある（`_find_column_positions`）。

地名文字列（「〇〇市〇〇地先」形式）は国土地理院の地名検索API
（`msearch.gsi.go.jp/address-search/AddressSearch`）でジオコーディングする。
字・大字レベルの精度（番地は解決しない）。東京都・埼玉県の対象934件のうち
**933件（99.9%）をジオコーディング成功**。要因施設の内訳は「下水道」が
**341件（36.5%）で最多**――本プロジェクトの前提（下水道管路の老朽化が道路陥没の
主要因）を実データが直接裏付けている。

## 5. 誠実性フレームワーク

README の表を参照。本書ではモデル単位で対応関係を明記する：

- **実データ**：`DisplacementVelocity`、`GroundClass.land_use_class`/`elevation_m`、
  `RoadExposure`、`SubsidenceEvent` はすべて上記5データソースからの実測・実取得値。
- **合成データ**：疑似管路（Triageモジュールで実装予定、`SyntheticPipe`相当のモデルは
  未実装）。
- **未実装（原理的制約ではなくスコープ判断）**：`PrecipitationObservation`（第6章）、
  `GroundClass.geology_class`/`ground_classification`（第2章）。

### 5.1 推論レベルの誠実性（第7章の確定判断を受けて）

上記はデータの「来歴」に関する誠実性である。第7章で確定した通り、Monitor解析レイヤー
（`backend/analysis/`）はさらに「推論の主張」レベルの誠実性を要求される。実装・審査の
双方で常に意識すべき既知リスクを、モデル単位で明記する：

- **標高の循環（`GroundClass.elevation_m`）**：本AOI（江東区・江戸川区）は「ゼロメートル
  地帯」であり、現在の低い標高は過去の地盤沈下の累積結果である。標高を「沈下を説明する
  独立変数」として扱う分析（例：残差回帰）は、沈下を沈下自身で説明する循環に陥る。この
  ため`backend/analysis/`では標高を回帰の説明変数として使わない。
- **地質データ未投入（`GroundClass.geology_class`）**：「地質で説明できない異常」という
  言い回しは、地質が実際にモデルへ入っていない限り虚偽ラベルになる。本プロジェクトは
  地質を分析に一切使わないため、この種の主張自体を行わない。
- **InSARのノイズフロア（`DisplacementVelocity.velocity_cm_per_year`）**：本AOI平均は
  -0.072cm/年（-0.72mm/年）で、GSI公表精度（概ね±数mm/年）の限界に近い。地図・API
  ともにセル単位の符号（沈下/隆起）を解釈しない旨を常設の注記として表示する
  （`backend/api/views.py`の`DISCLAIMERS`、フロントの`HonestyPanel`/`Legend`）。
- **字重心へのイベント集約（`SubsidenceEvent`）**：`ingest/kanbotsu_xlsx.py`のジオコー
  ディングは字・大字レベルの精度で、同一字内の複数件は同一座標にスナップされる。個々の
  イベントを精密な点として扱わず、常に「字（重心座標）単位の面」として集計・検定する
  （`backend/analysis/groundtruth.py`）。
- **n不足によるオーバーフィット**：AOI内の実イベント数は`report_aoi_events`コマンドで
  毎回実測し、下水道原因イベントが`PERMUTATION_TEST_MIN_N`（既定10）未満なら、いかなる
  統計的主張も行わず記述に留める。多変量回帰・スコアリングモデルの学習は本プロジェクトの
  どこにも実装しない（第7章）。

## 6. スコープ外とした判断

README の Future Work と併せて、判断の経緯を記録する。

**降水量データ**：計画段階では「解析雨量1kmメッシュ」を想定していたが、実際に
気象庁・国交省・JMBSC等のアクセス方法を調査した結果、**無償・自動・historical・
グリッド解像度の4条件を同時に満たす公式ルートが存在しない**と判明した：
DIAS/XRAINは長期メンテナンス中で復旧時期未定、気象庁の`obsdl`は自動化を明示的に
非推奨、無償の代替（`river.go.jp`）は1990年代フレームセット構成のサイトで
安定したスクレイピングが困難。当初のプラン段階で降水量は既に「susceptibility特徴量
にしない、局所陥没の引き金文脈のみ」に格下げ済みだった（circular/overclaim回避の
監査対応）ため、無理にスクレイパーを実装せず本PRのスコープから外した。

**ALOS-4自前SLC処理・自前InSAR時系列・クラウドデプロイ**：README参照。

## 7. Monitor解析レイヤーの設計判断（確定）

**Monitor解析エンジンの「加速度・トレンド変化検出」設計**。当初計画（時系列の2階差で
沈下の加速を検出）は、第4.1章の制約（GSIから得られるのは年度スナップショット1枚のみ）
により、稠密な時系列データを前提にした形では実装できないことが判明した。この制約を
受け、当初提示していた3つの選択肢を検討した：

1. **残差異常検出**：地質・標高・土地利用から「期待される沈下速度」を回帰し、実測速度
   との残差が大きいメッシュを「地質だけでは説明できない異常」として検出する案。
2. **点単位の時系列APIをさらに調査**：「時系列グラフ閲覧」機能の実際のAPIを調べ、
   メッシュ単位で稠密な時系列が取れないか確認する案。
3. **陥没密度回帰**：InSAR変位・地質・標高等を特徴量とし、道路露出をオフセットとした
   陥没報告密度の回帰分析を行う案。

### 7.1 却下の理由（独立した敵対的レビュー2回を経て）

- **Option 2（時系列API再調査）を却下**：第4.1章で「エリア一括の多時点時系列ダウンロード
  に対応するAPIは見当たらない」と実機検証済みであり、この選択肢の前提はすでに反証されて
  いる。選択肢として残すこと自体が誠実でない。
- **Option 1（残差異常検出）を却下**：`GroundClass.geology_class`が未投入のため、「地質
  で説明できない異常」という言い回しはモデルが統制していない変数についての虚偽ラベルに
  なる。加えて、標高を説明変数に使うと第5.1章で述べた循環（本AOIの低標高は過去の沈下の
  累積結果）に陥る。回帰のR²が低ければ残差はほぼ生の変位速度と同義になり、統計的加工の
  外見をまとっただけの生データ地図に帰着する。
- **Option 3（陥没密度回帰）も「回帰・スコアリングモデル」としては採用しない**：唯一、
  実在する外部イベント集合（MLIT陥没データ）に対して反証可能な検証ができる案ではあるが、
  AOI内の下水道原因イベント数は限られ（後述）、per-cellの連続的な「期待陥没率」を
  choropleth表示すると、nゲートで多変量係数が識別不能になった場合に実質「道路長の地図」
  をハザード色で偽装するだけになりかねない。これは面的トリアージ（README参照）の趣旨を
  超えた資産単位リスクの含意になり、誠実性フレームワーク（第5章）に反する。

### 7.2 確定した設計：記述統合＋グラウンドトゥルース重ね合わせ＋単一の付録検定

回帰・スコアリングモデルの学習は本プロジェクトのどこにも実装しない。代わりに
`backend/analysis/`は以下のみを行う：

1. **実データの面的統合**（`features.py`）：`MeshCell`ごとに変位速度・土地利用・標高・
   道路延長・観測イベント数を集約し`MeshSummary`として永続化する。予測・スコアは含まない。
2. **陥没イベントのグラウンドトゥルース重ね合わせ**（`groundtruth.py`、フロント
   `MonitorMap.tsx`）：実陥没を点overlayとして地図に重ね、共起を視覚的に検証可能にする。
   イベントは常に「字（重心座標）単位の面」として扱う（第5.1章）。
3. **AOI内実イベント数の正直な実測と開示**（`report_aoi_events`コマンド、
   `groundtruth.count_aoi_events`）：モデル化・検定の可否を判断する前に、まずnを測る。
4. **nゲートを通過した場合のみ、単一の空間パーミュテーション検定を付録として実施**
   （`permutation.py`）：「陥没(下水道原因)を含むセルは、含まないセルより変位速度が
   負に偏るか」を、道路曝露のある適格セルの母集団からのランダム再配置による正確検定で
   評価する。イベントは検定のターゲットとしてのみ使われ、モデルの入力特徴量には一切
   使わない（反循環）。`PERMUTATION_TEST_MIN_N`（既定10）未満なら検定自体を実施せず、
   その旨と理由を`AnalysisRun.metrics_json`に記録して正直に開示する。

### 7.3 実測結果（2025年度データ、AnalysisRun初回実行）

`report_aoi_events`の実測：AOI内 陥没イベント総数 **129件**、うち下水道原因
**30件**（占有字数25）。これは`PERMUTATION_TEST_MIN_N=10`を上回るため、付録検定を
実施した。結果：観測差 **+0.0216 cm/年**（陥没セルの平均変位速度は非陥没セルよりわずかに
正寄り＝隆起側。仮説と逆方向）、片側p値 **0.962**、両側p値 **0.122**（N=10,000回の
パーミュテーション、seed=42、k=25）。

**この結果は仮説を支持しない**。すなわち、本AOI・本データにおいて「陥没箇所は変位速度が
より負に偏る」という主張を統計的に裏付けることはできなかった。誠実性フレームワークの
原則どおり、この否定的な結果をそのまま公表する（README・HonestyPanel参照）。これは失敗
ではなく、検定機構が意図通りに機能し、都合の良い結果を選ばずに正直な結論を出したことの
証左である。
